# Контекст проекта: авторизация в Chaevarka

## Что за проект
Бэкенд для умной чаемашины (FastAPI + PostgreSQL). Мобильное приложение создаёт заказы на заварку, физическое устройство их забирает и выполняет.

## Стек авторизации
- **fastapi-users** — регистрация, логин, верификация email, сброс пароля
- **BearerTransport** — токен передаётся в заголовке `Authorization: Bearer <token>`
- **DB-backed токены** — токены хранятся в таблице `accesstoken`, при logout удаляются
- Токены **не истекают** (нет refresh-токенов, нет TTL — если он не выставлен в конфиге)

## Модель пользователя
```
users
├── id, email, hashed_password
├── is_active, is_verified  ← верификация есть, но НЕ обязательна для входа
├── first_name, last_name, phone, profile_picture
└── device_id → FK → devices.device_id  ← пользователь привязан к устройству
```

## Защита эндпоинтов (кратко)

### Публичные (без токена)
- `POST /auth/register` — регистрация
- `POST /auth/login` — получить токен
- `POST /auth/verify` — подтвердить email (токен из письма в теле)
- `POST /auth/forgot-password`, `POST /auth/reset-password`
- `GET /devices/{device_id}` — IP устройства
- `POST /devices` — устройство регистрирует себя
- `GET /tea-make/{device_id}` — устройство забирает заказ
- `POST /tea-make/{order_id}/complete` — устройство завершает заказ
- `GET /tea-make/{order_id}/status`, `PATCH /tea-make/{order_id}/status`
- `GET /recipes/` — публичные рецепты
- `GET /drums/config`, firmware download/check, `/ping`, `/health`

### Требуют токен пользователя
- `POST /auth/logout`
- `GET/PATCH/DELETE /users/me`
- `POST /tea-make` — создать заказ
- `POST /tea-make/{order_id}/cancel`, `/dispense`
- `GET /recipes/my`, `POST/PATCH/DELETE /recipes/`

### Только суперпользователь
- `DELETE /devices`, `DELETE /tea-make`
- `POST /drums/config`, `POST /upload` (прошивка)

## Верификация email — как работает сейчас
1. После регистрации письмо **не отправляется автоматически**
2. Приложение вызывает `POST /auth/request-verify-token` (нужен токен) → сервер шлёт письмо
3. Ссылка в письме ведёт на серверный HTML-view `GET /verify-email/?token=...` — пользователь кликает в браузере, сервер сам верифицирует
4. Войти можно и без верификации (`requires_verification=False`)

Три связанных проблемы:

**1. Привязка устройства к пользователю не работает нормально**
Сейчас `users.device_id` — просто поле в таблице пользователя. Непонятно как оно устанавливается. Устройство регистрирует себя через `POST /devices` (публичный эндпоинт, без токена) — но при этом нет механизма сказать серверу "это устройство принадлежит вот этому пользователю".

**2. Нужна поддержка нескольких пользователей на одном устройстве**
Сейчас схема: один пользователь → одно устройство (`users.device_id`). Нужно наоборот: одно устройство → несколько пользователей. Например, вся семья пользуется одной чаеваркой.

**3. Предложение: ключ/код для привязки**
Идея — устройство при первом включении генерирует или получает какой-то код/ключ. Пользователь вводит его в приложении и тем самым привязывает себя к устройству. Детали реализации надо обдумать.
